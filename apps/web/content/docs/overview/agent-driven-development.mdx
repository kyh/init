Init is built to be driven end-to-end by a coding agent — from a cold clone to a verified, running feature — without a human babysitting each step. This page is that workflow; [`AGENTS.md`](https://github.com/kyh/init/blob/main/AGENTS.md) at the repo root is the same guide your agent reads in-context.

## One-command provisioning

```bash
pnpm install
pnpm bootstrap --yes
```

`pnpm bootstrap` starts local Supabase, writes `.env`, pushes the schema, and seeds a dev user. It's interactive by default (a checklist to trim platforms you don't want), but `--yes` — or any piped, non-TTY invocation, which is how an agent runs it — keeps all apps and runs unattended. It needs Docker for local Supabase, and it's idempotent: re-run it, or `pnpm db:reset`, any time.

## A seeded login

Every provision leaves a known account, so an agent can verify authenticated flows with no signup step:

```
dev@init.local / password
```

It comes with a personal organization and a few sample todos (see `packages/api/src/seed.ts`). The seed goes through better-auth's own signup API, so it exercises the same organization-provisioning path a real user hits.

## Verifying a change

Three gates, cheapest first: static proves it compiles, smoke proves it runs, agent-browser proves the UI works. CI runs the first two on every commit.

**Static gate** — mirrors CI, run before every commit:

```bash
pnpm verify   # typecheck · lint · format · test
```

**Smoke gate** — the part most templates skip. Passing types isn't proof the app boots, that auth works, or that a mutation reached the database. `pnpm smoke` drives a _running_ server over plain HTTP and fails with the step that broke:

```bash
pnpm dev:web &
pnpm smoke
```

```
  ✓ server is live (/api/health)
  ✓ signed in as dev@init.local
  ✓ read the seeded todos
  ✓ created a todo
  ✗ todo.update did not persist `completed`
```

It needs no browser and nothing installed, so CI runs it on every commit against a real Supabase instance (see `.github/workflows/ci.yml`). Point it at a deployment with `SMOKE_URL=https://my-app-git-branch.vercel.app pnpm smoke` to verify a preview build instead of a local server.

**UI** — Init ships [agent-browser](https://github.com/vercel-labs/agent-browser) so an agent can drive the real web app:

```bash
npm i -g agent-browser && agent-browser install
agent-browser open http://localhost:3000
agent-browser snapshot           # accessibility tree with @eN refs
agent-browser fill @e1 dev@init.local
agent-browser click @e3          # sign in, then 'get text' / screenshot to assert
```

The web app is the one surface an agent can drive headlessly. Mobile, desktop, and extension build and typecheck, but a runtime check on those needs a human — see the matrix below.

## OAuth without the internet

Email/password needs nothing external. For the **GitHub** button, Init wires [emulate](https://github.com/vercel-labs/emulate) — a local OAuth provider — so the shipped button works offline in dev. Uncomment `NEXT_PUBLIC_GITHUB_EMULATOR_URL` in `.env`, then:

```bash
pnpm emulate
pnpm dev:web
```

With the var set, the "Continue with GitHub" button routes through a dev-only `genericOAuth` provider aimed at the emulator — the same button, no diverging prod path (unset ⇒ the real provider). Click it and the emulator's user-picker completes sign-in. Fixtures live in `emulate.config.yaml`.

## What an agent can verify

| Platform           | Dev command          | Runtime-verifiable by an agent         |
| ------------------ | -------------------- | -------------------------------------- |
| Web (Next.js)      | `pnpm dev:web`       | **Yes** — `pnpm smoke` + agent-browser |
| Mobile (Expo)      | `pnpm dev:mobile`    | No — needs a simulator/device          |
| Extension (WXT)    | `pnpm dev:extension` | No — real Chrome                       |
| Desktop (Electron) | `pnpm dev:desktop`   | No — GUI window                        |

## Two agents on one machine

Parallel agents mean parallel checkouts, each wanting a web server and a Supabase stack. `pnpm bootstrap` claims a free web port and a free Supabase port block on first provision, then pins both — `PORT` in `.env`, the block in `packages/db/supabase/config.toml`. Docker volumes are already namespaced per folder. The second checkout lands beside the first instead of on top of it, so read the port out of `.env` rather than assuming 3000.

Auth follows suit: `baseUrl` derives from `PORT` in dev and from `VERCEL_URL` on a preview deployment, so redirects and OAuth callbacks work in both without configuration.

## Shipping a change behind a flag

A flagged change is reversible without a revert — flip one environment variable and redeploy. Declare the flag in `packages/api/src/flags/flags.ts`:

```typescript
export const flagDefaults = {
  myFeature: false,
} as const satisfies Record<string, boolean>;
```

The registry is the only source of flag names, so a typo at a read site is a type error rather than a flag that reads `false` forever. Read it server-side as `ctx.flags.myFeature`, or on any client via the `flag.list` query.

```bash
FEATURE_FLAGS="myFeature"         # on
FEATURE_FLAGS="myFeature=false"   # off, explicitly
```

Set it per Vercel environment to land a change dark: on for preview, off in production, until a human decides. That is what makes an agent's change atomic — it goes in without changing what users see, and comes out without a git operation.

## Tracing a failed call

Every tRPC call emits one JSON line, and the request id in it comes back on the response as `x-request-id`:

```text
{"ts":"2026-08-05T…","requestId":"5f3c…","type":"mutation","path":"todo.create","durationMs":18,"ok":false,"code":"UNAUTHORIZED"}
```

Take the id off a failed response, grep the server output for it, and you have the record of that exact call — no correlating by timestamp. CI dumps these logs when the smoke gate fails, so a red build explains itself without a rerun. See `packages/api/src/observability/logger.ts`.

## The rest of the surface

Setup and verification are the runnable half of Init's agent story. The rest is context an agent loads on its own:

- **`AGENTS.md` + `CLAUDE.md`** — conventions and this workflow, read automatically
- **`llms.txt`** and **markdown negotiation** — the docs as machine-readable text
- **`/.well-known/api-catalog`** — endpoint discovery, including the `/api/health` probe
- **[Agent wiki](/docs/build/agent-wiki)** — an optional OpenWiki job that keeps a generated map current

See [Local Development](/docs/overview/local-development) for the human day-to-day workflow.
